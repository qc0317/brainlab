多邻国产品全景图：从产品事实反推设计

阅读说明

这份全景图先回答“多邻国到底有什么”，再回答“这些东西怎样组织”，最后才讨论“为什么这样设计”。它不是把官方文章重新排列，而是建立一个可操作的产品模型。每一条内容都标注为：**公开观察**（官方帮助、产品文章或页面直接说明）、**界面观察**（可从公开截图和页面看到的状态）、**设计推断**（根据结构和行为推测的目的）、**待验证**（需要当前版本实测、访谈或数据确认）。不同国家、课程、平台、订阅等级和版本可能出现差异，不能把某一个截图当作全部用户的固定界面。

一、先认识多邻国是什么产品

多邻国是一个把学习内容、练习工具、游戏化奖励、社交关系和商业化服务合在一起的学习平台。它的主承诺是让用户随时完成一小段可理解的学习，而不是一次性读完一套教材。用户可以在移动端或网页端学习语言，也可以在部分地区使用数学、音乐、象棋等内容。产品的核心单位不是“看完一章书”，而是“今天完成一个可以立即开始的动作”。

**公开观察：**官方将课程描述为围绕沟通目标组织的单元；单元覆盖实现目标所需的词汇和语法，并在练习中混合听、说、读、写。课程路径会逐步提高题型难度，用户可以看到自己的课程位置、练习、进度和奖励。官方还公开介绍了 Duolingo Score、经验值、宝石、连胜、好友任务、Feed、排行榜和成就等系统。

**设计推断：**多邻国不是单一课程，而是一个“内容操作系统”。课程提供学习理由，任务提供每日入口，奖励提供即时反馈，社交提供关系承诺，订阅提供资源边界。任何一个功能都要放回这个系统理解：例如宝石不是单纯的虚拟货币，它同时是补救连胜、购买加成、兑换练习机会和展示积累的接口。

**待验证：**不同用户看到的标签、图标、生命和任务是否一致；语言课程、数学、音乐和象棋是否共用完全相同的路径模型；当前版本的 Score 是否在所有课程和平台开放。

二、课程和内容地图

2.1 课程类型

课程首先按学习对象分组。语言课程是最成熟的主线，包含从零开始的语言路径、多个语言方向和不同母语背景的课程版本。除语言外，官方还推出数学和音乐等非语言课程，并持续测试新的学科或游戏化学习内容。课程可分为：

1. **主课程路径**：围绕从基础到更高沟通目标的连续内容。 2. **复习与练习**：回看已学内容、强化薄弱题型或进行个性化复习。 3. **故事、情境和角色内容**：把语言放入对话、阅读或任务场景。 4. **专题活动**：围绕节日、角色、电影、旅行或合作目标组织的短期内容。 5. **其他学科课程**：复用短练习、路径和奖励框架，但材料和能力定义不同。

课程名称和可用模块可能随地区、语言方向、客户端和时间变化。研究时必须记录课程语言、母语方向、平台、版本日期和是否登录；否则“这个功能有没有”没有可复核含义。

2.2 课程的层次结构

可把用户看到的主路径抽象为：

课程 Course
└── Section / 大章节
    └── Unit / 单元
        └── Lesson path / 练习路径
            └── Level / 关卡层级
                └── Lesson / 一节课
                    └── Exercise / 单题

这是一种分析模型，不保证每个版本都使用完全相同的中文标签。官方近年的课程说明明确使用 Section、Unit 和沟通目标；公开界面也显示单元标签、课程位置、完成状态和 Score。用户通常不是从“整门课程目录”开始，而是从当前路径中的下一个可行动节点开始。

2.3 Section：长期范围

Section 是较长时间范围的内容分区。它可以对应某一组能力、主题、词汇和语法目标，并显示用户在该部分的 Score 或完成状态。Section 的作用是让用户知道自己处于课程的哪一段，支持回看已完成部分，也让长期目标有一个可见的地图。

**设计推断：**Section 把“学会一门语言”变成有限的远期地标。它不是每天都要操作的单位，而是帮助用户解释长期进度和能力范围的导航层。

2.4 Unit：沟通目标

Unit 是课程内容的主要编排单位。一个 Unit 聚焦有限的沟通目标，并组织实现这个目标所需的词汇、语法和题型。Unit 的设计价值在于提供语义场景：用户不是孤立地背单词，而是在目标情境中反复识别、理解、回忆和生成。

Unit 通常由多个连续的练习节点组成。早期节点可能要求识别或选择，后续节点逐渐要求输入、听辨、翻译、朗读或在干扰下回忆。研究者需要把“内容目标”和“操作难度”分开记录：同一 Unit 可以增加题目数量，也可以增加延迟、干扰、生成要求或听力负荷。

2.5 Level / 关卡层级

Level 是 Unit 内的进度台阶。它可以通过重复相同主题、改变题型、提高难度或要求达到更高完成条件来表达“再练一次”。部分版本还使用 Legendary 或类似的高难度完成状态。Level 的产品作用是把一节课的即时完成与 Unit 的中期熟练联系起来。

**待验证：**当前版本每个 Unit 的 Level 数量、是否固定、是否按用户表现动态变化，以及 Legendary 是否在所有课程开放。不能用历史截图推断当前规则。

2.6 Lesson：每日最小行动

Lesson 是用户实际完成的一次短练习。它包含若干 Exercise，通常在几分钟内完成。用户开始 Lesson 后，界面会提供题目、输入方式、提示或跳过选项；提交后立刻显示对错、解释或下一题。Lesson 结束时，系统汇总经验、连胜、任务进度和可继续的入口。

用户每日任务通常落在 Lesson 层，而不是直接落在 Section 或 Unit 层。一个“完成一节课”可能同时满足：延长 Streak、增加 XP、推进每日任务、增加月度 Quest Points、推进好友任务和更新课程路径。也就是说，一个具体 Lesson 是多个系统共同监听的事件源。

2.7 Exercise：单题状态机

单题可以抽象成：展示题干 → 用户输入或选择 → 提交 → 正误判断 → 反馈与解释 → 进入下一题。题型包括配对、选择、听辨、翻译、填空、朗读、听写和自由输入等，具体可用性依课程和平台而变。

每道题至少有六种研究状态：未开始、输入中、已提交、正确、错误、退出或恢复。错误不只是红色提示，它可能触发扣除 Hearts、安排复习、改变任务进度或影响用户对难度的判断。研究记录需要保存题型、目标能力、输入方式、提示、错误原因、耗时和下一步，而不是只截图最终页面。

三、用户一天的行为落在哪个结构上

用户日常使用可以画成一条跨层路径：

打开 App
→ 首页/学习标签
→ 当前 Course Section
→ 当前 Unit
→ 下一组 Level
→ Lesson
→ 多个 Exercise
→ 结果页
→ XP / Score / Streak / Quest / Friend 状态更新
→ 通知、Feed 或下次回访

每日目标可能是完成一次 Lesson，也可能是获得一定 XP、完成特定题型、完成一次复习或参加社交任务。任务系统不一定要求用户理解全部层次；它通过一个主按钮把用户送入当前最有可能完成的节点。产品设计的关键是让用户能回答：我现在在哪里、今天做什么、完成后哪些系统会更新、如果我只做五分钟该怎么退出。

四、课程之外的完整内容系统

4.1 Monthly Quest：月度特别任务

月度 Quest 是围绕一个月的目标、角色或主题组织的任务集合。官方设计文章展示过“Zari’s Movie Binge”等月度 Quest，并说明新版本会把每日任务和好友任务放在统一的 Quest 体验中。用户完成每日挑战或好友任务，累积 Quest Points，达到里程碑后领取徽章或奖励。

**结构：**月份或主题 → 月度进度 → Daily Quest / Friends Quest → Quest Points → 里程碑 → Badge / Reward。

**设计价值：**它为每天重复的课程行为增加时间盒和叙事包装。用户不只是“又做了一课”，而是在一个月内推进一个可收集的目标。

**待验证：**任务数量、里程碑阈值、奖励类型、是否可补领和是否所有地区同步开放。月度活动不是永久课程内容，应单独记录起止日期。

4.2 专题型游戏与 Side Quest

课程路径中的角色、世界地图和 Side Quest 把练习包装成额外的情境挑战。Side Quest 可以要求用户完成一个关卡、特定题型或短对话，并通过角色颜色、动画和阶段性奖励表达进展。它们通常与主课程共享内容素材，但提供不同的入口、叙事和完成理由。

分析时要区分三种“游戏”：第一是课程练习本身的游戏化反馈；第二是围绕课程内容的 Side Quest；第三是独立的小游戏或学科产品。它们的目标、规则和能力结果不能混为一谈。

4.3 Leaderboard 与 League

排行榜是周周期竞争系统。官方公开说明显示，用户按时区和相似学习习惯进入一组跨课程的 League；每周开始和结束，用户根据 XP 排名上升、保持或下降。历史上从少数 League 扩展到更多层级，并存在 Diamond Tournament 等阶段性竞争。

**层次：**本周 League → 当前排名 → 晋级/保级/降级区间 → 周结束结果 → 下一周匹配。

**产品作用：**把个人完成转成公开比较，为本来没有共同课程的用户提供共同尺度。**风险：**XP 不是语言能力，排名也不是学习质量；高频低难度活动可能放大分数而不是能力。用户可以关闭公开档案或退出排行榜，隐私和压力应作为一等设计问题。

4.4 Feed 与消息中心

官方说明中，底部铃铛或 Feed 入口可以承载好友动态、里程碑、产品公告和社交提醒。消息中心不是单纯通知列表，而是把个人进展、好友行为和官方活动放在一起的关系层。

可拆分为：

  • **系统消息**：任务开始、奖励到账、版本功能和订阅提示；
  • **关系消息**：好友完成 Streak、获得成就、发送鼓励或邀请；
  • **召回消息**：今日未完成、连胜风险、好友任务待推进；
  • **内容消息**：新课程、专题活动、角色或联动内容。

研究消息中心时，必须记录消息来源、优先级、是否可关闭、是否有深链接、点击后落到哪个页面，以及消息是否改变了用户的下一步。通知发送成功不等于用户理解或完成。

4.5 个人档案、Avatar、成就和徽章

个人档案是用户的身份页面和社会可见页面。它通常聚合头像或 Avatar、学习语言、Streak、好友、League 成绩、成就、徽章、个人记录和公开状态。官方成就改版文章说明，成就被集中放在档案中，既包括添加好友等早期行为，也包括长期连胜、每日 XP、完美课程和最高 League 等个人记录。

Avatar 的设计可以承担三种作用：身份识别、个性表达和奖励展示。Avatar 装饰或角色资产不应与真实能力混淆；它们表达“我是谁”和“我完成过什么”，不是医学或教育评级。

徽章设计通常使用里程碑、个人最佳和特殊行为三类逻辑。徽章页面把长期积累变成可浏览的收藏架，使过去行为能持续回到用户视野。对 BrainLab 的可迁移原则是：成就应该记录过程和坚持，同时允许用户隐藏健康相关或敏感活动，避免档案泄露个人状态。

4.6 动态 App Icon、Widget 与外部入口

连胜产品会把 App Icon、Widget 或系统通知变成“应用外的提醒表面”。官方帮助和产品文章曾介绍过改变 App Icon 位置、Widget 显示当日连胜状态，以及在特殊活动中使用不同图标或视觉包装的做法。

这类设计的关键不是图标本身，而是把用户还没有打开 App 的时刻纳入回访路径：看到图标变化 → 产生识别或好奇 → 打开 App → 进入任务或领取奖励。它也可能造成通知疲劳、系统权限依赖和品牌过度打扰，因此要记录开关、频率和用户感受。

4.7 联动活动与限时奖励

节日、电影、体育赛事或文化事件可以成为主题皮肤、角色、任务和收藏奖励的外壳。用户提到的“世界杯每日登录送球衣”属于典型联动结构：外部事件提供时间和情绪，产品把每日登录或学习任务绑定到可收集的视觉奖励。

联动活动的结构是：事件主题 → 每日或阶段任务 → 收集进度 → 服装/道具/徽章 → 活动结束。它能增加短期回访理由，但不能让限时奖励取代课程价值。研究时必须保存活动时间、地区、平台、奖励条件和是否复刻，避免把一次性活动写成永久功能。

五、连胜、能量、Hearts 和 Gems 的关系

5.1 Streak：连续行为层

Streak 记录连续完成满足条件的学习日。它是时间轴上的行为指标，不是课程掌握度。Streak Freeze、补救和好友 Streak 让系统在“连续”与“允许生活中断”之间取得平衡。连胜设计最强的地方是把未来行为绑定到已经投入的过去，但也最容易制造损失压力。

5.2 Hearts：错误成本与节奏控制

官方 Duolingo 101 说明，错误会消耗 Hearts，达到一定错误次数后需要练习以恢复；用户可以用 Gems 获取 Hearts，订阅用户可能享有无限 Hearts。Hearts 不是纯粹的生命值，它同时限制快速冲过内容的速度，迫使用户复习并给错误一个可见成本。

研究 Hearts 时应问：错误发生后用户是否理解原因？恢复练习是否与错误相关？没有 Hearts 时用户是否仍能完成核心学习？如果付费解除限制，产品是在减少干扰还是把学习流变成付费墙？

5.3 Energy：跨产品的通用资源模型

用户所说的“能量机制”需要区分不同版本和产品。部分新体验会使用 Energy、体力或练习次数限制，部分语言课程更常见 Hearts。不能把 Energy 当作所有客户端统一存在的系统。逆向工程应记录资源名称、减少条件、恢复速度、是否可通过练习恢复、是否可购买、是否影响每日任务，以及资源耗尽后用户能做什么。

5.4 Gems：经济与补救接口

Gems 是产品内货币，可用于购买 Streak Freeze、时间加成、Hearts、礼物或活动奖励。它把学习行为、连续性保护和商店消费连接起来。Gems 的价值不只在兑换物品，还在于把“我已经积累了多少”变成可见的账户状态。

六、从产品反推设计的方法

不能只收集“多邻国有什么功能”，还要把每个功能反推成设计决策。使用下面的逆向模板：

| 观察到的产品表面 | 用户要完成的行为 | 系统状态 | 触发与反馈 | 可能的设计目的 | 待验证问题 | |---|---|---|---|---|---| | 月度 Quest | 在时间盒内持续回访 | Quest Points 增加 | 进度条、徽章、提醒 | 把重复行为包装成短期叙事 | 活动结束后是否提高长期留存 | | League 排名 | 每周获得更多 XP | 排名变化、晋级区 | 名次、区间、周结算 | 建立低成本社会比较 | 是否诱发刷分和压力 | | Hearts | 控制错误与练习速度 | 资源减少或恢复 | 红心、练习、商店 | 让错误具有成本并创造复习入口 | 用户是否理解错误而不是只怕犯错 | | Profile 徽章 | 展示身份和历史 | 成就解锁 | 个人记录、收藏架 | 把过去行为变成未来动机 | 徽章是否影响真实学习质量 | | 动态图标 | 在 App 外想起产品 | 系统图标状态改变 | 图标、Widget、通知 | 扩大回访触点 | 权限关闭后体验是否完整 |

每个机制都要继续追问：它是否是课程内容？是否是行为奖励？是否是社交信号？是否是商业化边界？它改变的是用户目标、操作成本、反馈速度、关系压力还是长期身份？只有完成这一步，资料才从功能清单变成产品研究。

七、BrainLab 后续研究的重点

第一阶段要完成版本化产品地图：在指定设备上从注册、选课、首次 Lesson、每日任务、Quest、League、Feed、Profile、商店、订阅和设置走一遍，逐屏记录入口、状态、按钮、错误、返回和深链接。第二阶段建立事件地图：把 `lesson_started`、`exercise_answered`、`lesson_completed`、`quest_progressed`、`streak_extended`、`heart_lost`、`gem_spent`、`league_rank_changed`、`feed_opened` 和 `badge_unlocked` 连接到用户旅程。第三阶段才分析留存、社交和 GUI 如何共同作用。

产品事实、设计推断和效果证据必须分层。官方文章可以证明某功能如何被描述，截图可以证明某一时刻的界面，用户测试可以证明是否理解，行为数据可以证明使用关联，随机或长期研究才可能支持更强的因果结论。多邻国的 XP、Streak 或好友任务数据不能直接证明 BrainLab 的认知训练有效。

八、界面信息架构：用户每天从哪里进入系统

8.1 底部导航与核心标签

近年的官方界面重构文章把核心标签视为一个整体系统，而不是若干互不相干的页面。可观察到的入口通常包括学习主线、Quest 或任务、排行榜、社交 Feed、Profile 等，具体数量和图标会随平台、地区和版本变化。每个标签都有自己的标题、颜色、状态条和卡片，但它们共享字号、间距、按钮和反馈语言。

**信息架构模型：**

底部导航
├── Learn：课程路径、当前 Unit、继续学习
├── Quests：每日、好友、月度 Quest 和奖励
├── Leaderboard：本周 League、排名和结算
├── Feed：好友动态、成就、系统消息
└── Profile：学习数据、头像、好友、成就、设置

这不是对所有用户当前界面的承诺，而是研究时应逐一检查的假设地图。对每个入口记录：图标、未读状态、首屏主任务、可返回位置、是否出现付费提示、是否可以在不完成任务的情况下离开。

8.2 首页与继续学习

首页的首要任务是减少“今天要从哪里开始”的决策。常见结构是把当前课程节点或 Continue 按钮放在最高层级，再显示连胜、每日目标、经验和辅助卡片。用户完成一课后，首页应能解释课程推进、任务推进和奖励更新之间的关系。

**交互状态记录表：**

| 状态 | 用户看到什么 | 主操作 | 系统更新 | 失败或退出 | |---|---|---|---|---| | 当日未开始 | 目标、连胜、当前路径 | 开始 Lesson | 建立会话 | 稍后提醒、关闭 | | Lesson 进行中 | 题目、资源、进度 | 输入并提交 | 记录答题与 Hearts | 暂停、恢复、退出 | | Lesson 完成 | XP、Streak、Quest | 继续或离开 | 写入多个任务 | 返回路径 | | Hearts 不足 | 练习、购买或等待 | 复习/补充 | 资源恢复或消费 | 退出到其他内容 | | 今日已完成 | 完成提示、加餐入口 | 复习或结束 | 保持状态 | 安静结束 |

这张表揭示一个重要事实：主界面不是静态首页，而是多个后台状态的汇总。设计研究不能只拍一张首页截图，还要拍“未开始、完成、资源不足、活动进行中、通知未读”等变化。

8.3 首次使用与分流

首次使用通常会询问学习目标、语言、经验水平、每日目标或提醒偏好，并引导用户完成一小段体验。研究时要把首次使用拆成：价值承诺、目标选择、难度选择、第一题、第一次错误、第一节完成、注册或权限请求、提醒设置和第二次回访。

产品设计的关键不是收集最多信息，而是尽快让用户获得一次“我完成了”的证据。目标选择也不应被当作永久画像；用户需要能够修改语言、目标、每日时长和通知设置。待验证问题包括：注册前是否能完成体验、不同选择是否真的改变路径、用户是否理解每日目标和课程进度的区别。

九、任务系统的完整时间尺度

多邻国的任务不是一个列表，而是多个时间尺度叠加：

  • **单题任务**：几秒到几十秒，反馈是对错和提示；
  • **Lesson 任务**：几分钟，反馈是经验、完成动画和下一步；
  • **每日任务**：一天内完成若干目标，反馈是 Quest Points 或奖励；
  • **好友任务**：通常跨几天的共同目标，反馈是共享进度和鼓励；
  • **月度 Quest**：一个月的里程碑，反馈是徽章或收藏；
  • **League 周期**：一周的比较与结算，反馈是排名和晋级；
  • **长期课程**：数周到数月，反馈是 Section、Unit 和 Score 的进展。

同一个 Lesson 可以同时为多个时间尺度贡献一次事件。这解释了为什么结果页会同时出现 XP、Streak、Quest、好友和课程进度。对 BrainLab，未来也应避免把所有目标压缩成一个“分数”；应该明确区分一次训练、当天节奏、周目标、长期能力和独立结果。

十、商店、订阅与商业化边界

商店是资源系统的消费界面，可能包含 Gems、Streak Freeze、时间加成、练习机会、Hearts 或其他活动道具。订阅则可能提供去广告、无限 Hearts、额外练习、进阶反馈或家庭共享等权益。不同市场和时期的权益会变化，因此研究记录必须包含价格地区、货币、周期、试用、自动续费、取消入口和截图日期。

商业化流程可以拆为：触发限制 → 展示权益 → 价格与周期 → 确认支付 → 成功/失败 → 恢复购买 → 取消或退款。每一步都要记录是否阻断核心 Lesson、是否能返回、是否有误购保护、是否把疾病或焦虑用于促销。对 BrainLab，健康语境中的付费不能暗示“支付更多就能预防阿尔茨海默病”，也不能用失去连续性制造不必要压力。

十一、动态内容和版本差异的记录规范

多邻国更新频繁，且存在 A/B 测试、灰度发布、平台差异、课程差异和地区差异。一个可靠的产品档案必须有以下字段：

| 字段 | 记录内容 | |---|---| | 观察日期 | 年月日和时区 | | 客户端 | iOS、Android、Web、桌面或学校版 | | 版本 | App 版本、网页版本或文章发布日期 | | 账号状态 | 新用户、回归用户、订阅、家庭组 | | 课程上下文 | 语言方向、Section、Unit、课程类型 | | 功能状态 | 开启、关闭、灰度、未出现 | | 证据类型 | 官方文档、截图、实测、访谈或推断 | | 可复现性 | 另一个账号或设备是否能看到 | | 变化记录 | 与上一次观察相比新增、删除或改名 |

没有这些字段时，“多邻国有能量”“多邻国有某个按钮”都只能算未限定的陈述。研究资料应保留历史版本，而不是覆盖旧截图；因为设计变化本身就是产品策略的证据。

十二、从页面反推数据模型

把界面转成数据库时，可以使用以下实体关系：

User
├── CourseEnrollment ── Course / Section / Unit / Level
├── LessonSession ──── ExerciseAttempt
├── DailyGoal / Streak / Score / XP
├── QuestProgress ───── MonthlyQuest / DailyQuest / FriendsQuest
├── SocialGraph ─────── Friend / FriendStreak / League
├── Profile ─────────── Avatar / Achievement / PersonalRecord
├── Wallet ──────────── Gems / Hearts / Energy / Item
├── Notification ────── FeedEvent / DeepLink
└── Subscription ────── Plan / Entitlement / BillingState

每个实体都应有版本和时间。课程内容更新后，同一道题的题目版本可能不同；Quest 结束后，历史进度不能被覆盖；League 结算后，排名需要保留快照；Badge 解锁需要记录触发事件。这样才能回答“用户当时为什么得到这个奖励”，而不是只显示一个当前数字。

十三、产品研究的判断顺序

以后分析多邻国的任何功能，都按七步执行：

1. **命名功能**：它在界面上叫什么，用户从哪里进入？ 2. **确认边界**：它属于课程、任务、社交、身份、资源还是商业化？ 3. **画状态**：未开始、进行中、成功、失败、过期、恢复和退出分别怎样？ 4. **找事件**：什么行为触发更新，哪些指标被同时写入？ 5. **看反馈**：文字、颜色、动画、声音、震动、通知和档案如何表达？ 6. **推断目的**：它降低了什么成本，增加了什么动力，又制造了什么风险？ 7. **提出验证**：需要实测、访谈、可用性实验还是长期行为数据？

这个顺序能避免“看到一个徽章就说它提高留存”或“看到一个排行榜就说它促进学习”。先描述事实，再构造机制假设，最后寻找证据。

结论

完整理解多邻国，需要先把它看成一个由课程树、练习状态机、任务日历、奖励经济、社交图谱、身份档案、消息系统、外部触点和商业化边界组成的产品系统。课程是主干，Lesson 是每日行动，Exercise 是交互单位；Quest、League、Feed、Profile、Badge、Streak、Hearts、Gems 和联动活动围绕这条主干反复召回、反馈和赋予意义。

后续专题不再从“多邻国很有粘性”这种结论开始，而从每一个页面、每一个状态和每一条事件链开始。先知道它是什么，再分析它为什么这样设计，最后判断哪些机制适合 BrainLab、哪些机制必须改写或拒绝迁移。
