# 多邻国功能百科与逆向设计卡

## 功能卡的判读方式

本页把功能拆成“用户看见的表面、产品承担的任务、后台可能记录的状态、设计作用和验证要求”。公开资料只能证明功能被官方描述过，不能证明当前所有用户都能看到，也不能直接证明它提高了学习能力。每张卡都要补充平台、地区、版本、账号状态和截图来源。

## 月度特别任务 Monthly Quest

**表面：**带有月份、角色或主题的任务页，显示每日任务、好友任务、点数、进度条和里程碑。官方界面重构文章展示过以角色和电影主题包装的月度 Quest。

**用户任务：**在一段有限时间内持续完成短任务，达到节点并领取徽章或奖励。

**状态模型：**未开始 → 当月进行中 → 今日任务完成 → 点数累计 → 里程碑可领取 → 当月结束/过期。需要记录补领、跳过、重置和活动结束后的历史显示。

**设计推断：**把日常重复行为放进一个月度叙事，让“做一节课”拥有收藏和时间盒意义。它同时创造新鲜感和回访理由。

**待验证：**月度任务是否所有课程、地区和平台一致；任务阈值是否按用户分层；活动奖励是否影响下月留存；过期是否制造过强的错过压力。

## Daily Quest 与 Friends Quest

Daily Quest 把一天的目标拆成多个可以完成的动作；Friends Quest 把数日目标分配给朋友或小组。官方说明显示，好友任务可由系统匹配互相关注且近期活跃的朋友，双方共同积累进度，并能发送预设鼓励或 XP Boost。

**逆向结构：**任务模板 → 资格判断 → 分配/邀请 → 个人贡献 → 共享进度 → 提醒和鼓励 → 奖励/失败恢复。后台需要记录任务版本、成员、目标、贡献、剩余时间、提醒、退出和奖励领取。

**设计推断：**Friends Quest 不要求双方同时聊天，使用“并肩学习”取代高成本社交表达；共享进度让个人行为获得关系意义。

## 专题游戏与 Side Quest

专题游戏不是一个单一类别。研究时要分为：

1. 课程内题型的游戏化包装；
2. 与角色、故事和世界地图绑定的 Side Quest；
3. 独立的学科或小游戏产品；
4. 限时活动中的互动任务。

每种类型都要记录是否使用课程知识、是否有独立规则、是否产生 XP、是否消耗 Hearts/Energy、是否计入 Streak，以及结束后是否回到主课程。否则“专题游戏”会把不同的教育和增长机制混在一起。

## League、Leaderboard 与 Tournament

**表面：**本周排名、用户 XP、晋级区、降级区、其他成员、结算时间和奖励。官方公开说明中，League 按周运行，用户通常与学习习惯和时区相近的人匹配，竞争可以跨语言课程；Diamond Tournament 另有阶段性淘汰。

**状态：**等待本周开始 → 已匹配 → 进行中 → 接近结算 → 晋级/保级/降级 → 历史结果。排名不是用户能力测量，而是一个有限时间内的 XP 排序快照。

**设计推断：**它把陌生用户组织成低承诺竞争组，利用周周期制造回访和目标。匹配“相似习惯”可以降低一开始就被重度用户碾压的感觉。

**风险：**刷低难度 XP、时区和设备差异、公开健康或学习状态、失败羞耻、过度竞争。必须提供关闭公开档案或退出排行榜的路径。

## Feed 与消息中心

Feed 是关系动态、成就和官方消息的混合入口。消息中心可以按来源拆成：系统事件、好友事件、Quest 事件、召回事件、活动公告和商业化消息。每条消息都应有时间、未读状态、深链接、是否可关闭和过期规则。

**设计问题：**消息是否解释“为什么现在看到它”；点击是否落到可执行页面；完成动作后消息是否变成历史；用户能否按类型关闭；同一事件是否同时出现在 Push、Feed、Email 和 App Icon。

## Profile、Avatar 与个人身份

Profile 由身份、行为摘要、社交关系、课程进度和成就构成。Avatar 不是单纯装饰，它帮助用户在 Leaderboard、Friends Quest 和 Feed 中被识别，也让奖励成为可展示的身份变化。

**状态：**默认头像 → 自定义头像 → 成就或活动装扮 → 隐私限制 → 账号停用/删除。研究时要观察编辑是否即时保存、Avatar 是否同步到社交页面、未成年人和家庭账号有哪些限制。

## Achievement、Badge 与 Personal Record

官方成就文章将徽章集中到 Profile，并区分添加好友、连胜、每日 XP、完美课程、最高 League 等里程碑和个人纪录。成就系统的基本状态是：未发现 → 进度中 → 达成 → 弹出庆祝 → 进入档案 → 可分享或隐藏。

**设计推断：**徽章把过去行为变成可回看的收藏架，建立长期身份；个人纪录把“我超过了过去的自己”与“我超过了别人”分开。

**待验证：**成就是自动解锁还是需要领取；不同成就是否有稀有度和等级；成就是否影响任务推荐；用户是否能隐藏健康敏感的学习记录。

## Streak、Friend Streak 与 Streak Freeze

Streak 是按天计算的连续完成记录；Friend Streak 是由好友共同维护的共享连续性；Streak Freeze 是预先购买或获得的中断保护。它们都建立在“今天是否完成”这个事件上，但社会含义不同：个人 Streak 是自我承诺，Friend Streak 是关系承诺，Freeze 是中断风险管理。

**关键事件：**当天完成、临界时间提醒、冻结消耗、恢复、断裂、补救、好友未完成、共享提醒。研究不能只记录火焰数字，还要记录断裂后用户是否知道原因、能否恢复、是否受到羞辱或压力。

## Hearts、Energy 与练习生命

Hearts 通常与答错和练习恢复关联；Energy 可能出现在特定新体验或活动中。两者都属于“可消耗资源”，但它们的消耗条件、恢复方式和订阅权益可能不同，不能直接合并为一个机制。

**资源卡字段：**资源名称、最大值、减少事件、恢复时间、免费恢复方式、Gems 恢复、订阅权益、耗尽后可进入页面、是否影响 Streak、是否影响 Quest。

**设计问题：**资源限制是在帮助用户放慢并复习，还是在阻断核心学习？用户是否理解答错的教育意义，还是只把答错理解为失去生命？恢复练习是否与错误内容相关？

## Gems、Shop 与道具经济

Gems 是跨系统的经济接口，可由完成活动获得，也可用于 Streak Freeze、Hearts、加成、礼物或其他道具。Shop 将课程行为转为可消费的库存，必须区分一次性道具、订阅权益和活动收藏。

**状态：**余额显示 → 商品浏览 → 购买确认 → 扣除 → 道具到账 → 使用/过期 → 恢复或退款。每次消费需要记录商品版本、价格、地区、余额、来源、成功或失败以及撤销。

## 动态 App Icon、Widget 与召回

动态 App Icon 和 Widget 把连胜、活动或未读状态带到 App 外。它们不是独立功能，而是通知、系统权限、深链接和回访策略的组合。

**状态链：**触发资格 → 生成图标/Widget 状态 → 系统展示 → 用户点击 → 深链落点 → 完成或关闭 → 频率更新。研究时要记录权限关闭、安静时段、时区、图标变化是否解释清楚，以及用户能否仅凭图标理解下一步。

## 联动活动

联动活动以世界杯、节日、电影、角色或文化事件为外壳，把每日登录、完成课程、收集点数和兑换衣服/徽章/装扮连接起来。产品结构通常是：主题叙事 → 每日或阶段任务 → 收集进度 → 限时奖励 → 活动结束。

联动的设计价值是借用外部时间和情绪，让回访有一个短期理由；风险是活动奖励压过学习目标，或让错过活动的用户感到永久损失。研究档案必须记录起止日期、地区、平台、素材授权和奖励是否可复刻。

## 通知与订阅

通知按触发源分为：连胜风险、每日目标、好友互动、Quest 进展、活动公告、未读 Feed 和订阅/商店。每类通知应有频率上限、安静时段、分类关闭和深链接。

订阅流程要记录限制出现位置、权益说明、试用、价格、自动续费、取消、恢复购买和免费路径。商业化不能让用户误以为订阅能带来医疗保护，也不能用“今天不付费就退化”制造疾病恐惧。

## 一张完整产品事件链

```text
用户打开 App
→ 看到课程/任务/社交入口
→ 选择 Lesson 或 Quest
→ 完成 Exercise
→ 错误可能消耗 Hearts
→ Lesson 完成获得 XP
→ Streak、Daily Quest、Monthly Quest 更新
→ League 排名变化
→ Profile/Badge/Feed 可能产生新状态
→ 通知、Widget 或 App Icon 为下一次回访制造入口
```

这条链是多邻国产品研究的核心。它说明课程不是孤立的教学模块，而是整个奖励、社交、身份和召回系统的事件源。后续 BrainLab 的训练产品也应先绘制这类事件链，再决定哪些机制值得迁移。
